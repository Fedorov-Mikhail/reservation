# Reservation

Сервис бронирования ресурсов с REST API и веб-интерфейсом. Поддерживает расписания доступности, временные удержания, лист ожидания, пользователей и внутренние уведомления. Защита от пересекающихся броней обеспечивается транзакциями и ограничениями PostgreSQL.

## Технологии

| Компонент | Технологии |
| --- | --- |
| Backend | Java 21, Spring Boot 4.1.1, Spring MVC, Spring Security, Bean Validation |
| Данные | PostgreSQL, Spring Data JPA, JdbcTemplate, Liquibase |
| Frontend | React, TypeScript, Vite, CSS |
| Проверки | JUnit, AssertJ, интеграционные проверки PostgreSQL, Vitest, Playwright |
| Сборка | Maven Wrapper, npm |

## Структура репозитория

```text
src/main/java/com/mikey/reservation/
  resource/       ресурсы
  booking/        брони, удержания и транзакции
  availability/   поиск свободного времени
  identity/       учётные записи и права
  schedule/       недельные расписания и исключения
  waitlist/       очередь на освободившееся время
  notifications/  outbox и доставка внутренних уведомлений
  shared/         конфигурация, ошибки и логирование
src/main/resources/db/changelog/  миграции
src/test/                        проверки backend
frontend/                        веб-интерфейс
```

Backend организован как монолит с пакетами по предметным областям. В областях ресурсов и бронирований выделены API, прикладные сервисы, доменная модель и доступ к данным. Frontend обращается к API через прокси Vite.

## Требования к окружению

- JDK 21; переменная `JAVA_HOME` должна указывать на установленный JDK.
- PostgreSQL; интеграционные проверки выполнялись на PostgreSQL 18.
- Node.js 22.12 или новее; рекомендуемая версия для локальной разработки — 24.
- Maven устанавливать отдельно не требуется: в репозитории есть wrapper.
- Microsoft Edge для браузерных проверок с текущей конфигурацией Playwright.

## База данных и конфигурация

Создайте базу и отдельного пользователя приложения. По умолчанию используются база `reservation` и пользователь `reservation_app` на `localhost:5432`. Пользователю нужны права создания объектов в выбранной схеме. Миграции устанавливают расширение `btree_gist`; его можно предварительно установить от имени администратора БД.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DB_URL` | `jdbc:postgresql://localhost:5432/reservation` | JDBC URL |
| `DB_USERNAME` | `reservation_app` | Пользователь PostgreSQL |
| `DB_PASSWORD` | обязательна | Пароль PostgreSQL |
| `SERVER_PORT` | `8080` | Порт backend |
| `ADMIN_USERNAME` | не задана | Логин первого администратора |
| `ADMIN_PASSWORD` | не задана | Пароль первого администратора |
| `BACKEND_URL` | `http://127.0.0.1:8080` | Адрес backend для прокси Vite |

Liquibase применяет миграции при запуске. Hibernate проверяет схему (`ddl-auto=validate`). Секреты передаются через окружение, а не через исходники или README. Конфигурация приложения находится в `src/main/resources/application.properties`.

### Первый администратор

Перед первым запуском задайте обе переменные `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Логин: 3–64 строчных латинских букв, цифры, дефис или подчёркивание. Пароль: от 8 символов, не более 72 байт UTF-8.

После создания учётной записи обе переменные можно удалить. Пароль хранится как BCrypt-хеш. Повторный запуск с тем же логином не меняет пароль существующего администратора. Регистрация через API создаёт пользователя с ролью `USER`; повышение прав выполняет администратор.

## Локальный запуск

Из корня репозитория, с настроенными переменными окружения:

```powershell
.\mvnw.cmd spring-boot:run
```

Альтернатива: запустить `ReservationApplication` в IDE с JDK 21 и теми же переменными окружения. Переменные конфигурации IDE не распространяются на отдельные терминалы.

Проверка готовности backend: `GET http://127.0.0.1:8080/actuator/health`, ожидаемый ответ — `{"status":"UP"}`. Backend слушает `127.0.0.1`. Веб-интерфейс запускается отдельным процессом:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Адрес интерфейса: `http://127.0.0.1:5173`. Для остановки процесса используется `Ctrl+C`. Настройки и команды frontend описаны в [frontend/README.md](frontend/README.md).

## Аутентификация и права

Аутентификация использует HTTP-сессию с cookie `JSESSIONID`; время ожидания сессии — 30 минут. Cookie имеет флаги HttpOnly и SameSite=Lax. Для изменяющих запросов требуется CSRF-токен: получите `GET /api/v1/auth/csrf` и передайте поле `token` в заголовке `X-CSRF-TOKEN`, сохраняя cookie сессии. После входа токен следует получить заново.

Вход: `POST /api/v1/auth/login`, Content-Type `application/x-www-form-urlencoded`, поля `username` и `password`. Регистрация: `POST /api/v1/auth/register`, JSON с теми же полями. Пароль регистрации: 8–64 символа, не более 72 байт UTF-8. Логин нормализуется в нижний регистр.

| Операция | USER | Управляющий ресурсом | ADMIN |
| --- | --- | --- | --- |
| Просмотр ресурсов и доступности | Да | Да | Да |
| Создание брони, удержания или заявки | Да | Да | Да |
| Просмотр и отмена собственных броней | Да | Да | Да |
| Просмотр и отмена чужих броней | Нет | Нет | Да; для отмены нужна причина |
| Редактирование ресурса и расписания | Нет | Только назначенного ресурса | Да |
| Создание ресурсов | Нет | Нет | Да |
| Изменение ролей и назначение управляющих | Нет | Нет | Да |

Управляющий — назначение на конкретный ресурс, а не отдельная глобальная роль. В БД остаются роли `USER` и `ADMIN`. Последнего активного администратора нельзя отключить или понизить. Проверка прав выполняется backend независимо от видимости кнопок в интерфейсе.

### Ручная проверка прав

1. Используйте разные браузеры или отдельные профили для администратора и обычного пользователя. Обычные вкладки одного профиля разделяют сессию.
2. Зарегистрируйте пользователя. У него отсутствует раздел «Пользователи» и возможность создания ресурсов.
3. Администратором создайте два ресурса. Выберите первый, откройте «Пользователи» и назначьте зарегистрированного пользователя управляющим.
4. Обновите страницу пользователя, выберите первый ресурс: редактирование ресурса и расписания доступно. Для второго ресурса эти возможности отсутствуют.
5. Отзовите управление и обновите страницу пользователя: редактирование первого ресурса станет недоступным.
6. Создайте бронь обычным пользователем. Другой обычный пользователь не должен видеть её детали и отменять её. Администратор может отменить чужую бронь с указанием причины.
7. Повышение роли до `ADMIN` и последующее понижение проверяются после выхода и повторного входа, чтобы интерфейс загрузил актуальную учётную запись. Отключённый пользователь не может продолжить работу.

Для проверки API используйте CSRF-токен соответствующей сессии. Запрещённая операция возвращает `403`, запрос без действующей аутентификации — `401`.

## Основные API

Префикс: `/api/v1`. Входные даты — ISO 8601 с `Z` или явным смещением; ответы нормализуются в UTC. Идентификаторы ресурсов, пользователей и броней — UUID.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/auth/me` | Текущая учётная запись |
| POST | `/auth/logout` | Завершение сессии |
| GET / POST | `/resources` | Список / создание ресурсов |
| GET / PUT | `/resources/{id}` | Просмотр / изменение ресурса |
| GET | `/resources/{id}/permissions` | Право управления ресурсом |
| GET / PUT | `/resources/{id}/schedule` | Расписание ресурса |
| GET | `/resources/{id}/availability` | Свободные интервалы |
| POST | `/resources/{id}/bookings` | Создание подтверждённой брони |
| POST | `/resources/{id}/holds` | Временное удержание |
| GET | `/resources/{id}/bookings` | Список доступных текущему пользователю броней |
| GET | `/me/bookings` | Собственные бронирования |
| GET | `/bookings/{id}` | Детали брони |
| POST | `/bookings/{id}/confirm` | Подтверждение удержания |
| POST | `/bookings/{id}/cancel` | Отмена; опциональное тело `{"reason":"..."}` |
| POST | `/resources/{id}/waitlist` | Заявка в очередь |
| GET | `/me/waitlist` | Собственные заявки |
| POST | `/waitlist/{id}/cancel` | Отмена заявки |
| GET | `/me/notifications` | Внутренние уведомления |
| POST | `/me/notifications/{id}/read` | Отметка о прочтении |
| GET | `/admin/users` | Пользователи |
| PUT | `/admin/users/{id}` | Изменение роли и активности |
| PUT / DELETE | `/resources/{id}/managers/{userId}` | Назначение / отзыв управления |

Тело создания брони, удержания или заявки: `{"startsAt":"...","endsAt":"..."}`. Списки ресурсов и броней возвращают `items`, `page`, `size`, `totalElements`; пользователи, заявки и уведомления — массивы с постраничными параметрами. Размер страницы — от 1 до 100.

Поиск доступности требует `from` и `to`, поддерживает `minDurationMinutes`. Список броней поддерживает `status` и пару `from`/`to`; фильтр выбирает пересекающиеся с окном интервалы. Статусы: `HELD`, `CONFIRMED`, `CANCELLED`, `EXPIRED`.

## Бизнес-правила и конкурентность

- Интервалы полуоткрытые: `[startsAt, endsAt)`. Соседние брони 10:00–11:00 и 11:00–12:00 совместимы.
- Длительность — от минуты до 24 часов; начало не в прошлом, конец в пределах 365 дней. Окно поиска — не более 31 суток.
- Расписание содержит недельные рабочие интервалы, исключения по датам и зону ресурса. До настройки ресурс доступен круглосуточно в UTC.
- Удержание действует до 5 минут и не дольше оставшегося времени до начала брони. Его можно подтвердить, отменить; истёкшее удержание получает `EXPIRED`.
- Бронь можно отменить до начала. Отменённые записи сохраняются в истории.
- Очередь предлагает освободившееся время через удержание. Предложение требуется подтвердить до истечения срока.
- Изменение брони и запись события outbox выполняются в одной транзакции. Отдельный обработчик доставляет внутренние уведомления с повторами.

Создание брони блокирует строку ресурса. PostgreSQL exclusion constraint запрещает пересечения активных записей `HELD` и `CONFIRMED` для одного ресурса. Поиск доступности не резервирует время; окончательная проверка выполняется при записи в БД. API создания брони и удержания поддерживает `Idempotency-Key` для безопасного повторения одинакового запроса одним пользователем.

Время в интерфейсе вводится в зоне браузера, расписание задаётся в зоне ресурса. Дата просмотра расписания и даты формы независимы: бронь на другой день можно найти через выбор нужной даты или раздел «Мои бронирования».

## Ошибки и логирование

Прикладные ошибки возвращаются как `application/problem+json` с `status`, `code`, `detail` и `requestId`; ошибки валидации могут содержать `errors`. Ответы фильтров безопасности содержат `status` и `code`. HTTP-статусы: `400` — некорректные данные, `401` — отсутствие входа, `403` — недостаточно прав, `404` — объект не найден, `409` — бизнес-конфликт, `503` — временная недоступность.

Идентификатор запроса возвращается в `X-Request-ID` и используется в логах HTTP-запросов для сопоставления ошибки с серверной обработкой.

## Сборка и проверки

```powershell
# Unit-тесты без БД
.\mvnw.cmd test

# Unit- и интеграционные тесты; требуется PostgreSQL и DB_PASSWORD
.\mvnw.cmd verify

# Запуск собранного приложения с настроенным окружением
java -jar target/reservation-0.0.1-SNAPSHOT.jar
```

Интеграционные тесты используют случайную схему `reservation_it_*` в базе из `DB_URL`. Схема удаляется при нормальном завершении тестового JVM; при принудительном завершении она может остаться. Данные рабочей схемы не очищаются. Отчёты: `target/surefire-reports` и `target/integration-test-reports`. Docker для текущего набора проверок не требуется.

```powershell
cd frontend
npm.cmd test
npm.cmd run build
```

Браузерные проверки и их окружение описаны в [frontend/README.md](frontend/README.md).

## Текущие ограничения

Интеграция с внешними календарями, перенос бронирований, многопользовательская изоляция организаций и внешние каналы уведомлений ещё не реализованы. Текущая конфигурация рассчитана на локальный запуск. Для размещения frontend необходим веб-сервер с прокси `/api` к backend; Vite dev/preview используется при разработке.
